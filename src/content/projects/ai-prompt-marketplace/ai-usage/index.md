## AI에 대한 나의 생각

AI 도구는 소극적으로 곁들여 쓰는 보조 수단이 아니라 적극적으로 사용해야 한다고 생각합니다. 다만 그 적극성의 방향이 중요합니다. 구현(코드 작성) 자체는 AI에 맡겨 생산성을 최대한 끌어올리되, 그만큼 설계와 검증에는 오히려 더 많은 시간을 쏟아야 한다고 봅니다. AI가 짠 코드라도 최종적으로는 제가 이해하고 책임질 수 있어야 한다는 원칙을 지키려 했고, 실제로 이 원칙 덕분에 코드 리뷰에서 설계 의도나 구현 배경에 대한 질문이 들어왔을 때 막힘없이 답변할 수 있었습니다.

## 이 프로젝트에 AI를 어떻게 사용했는가

### 설계 논의

트러블슈팅 사례로 남긴 4건의 설계 결정 모두 Claude Code와 논의하며 만들었습니다.

- [결제 게이트웨이 호출 장애 전파를 막기 위한 회복성 계층 도입](/projects/ai-prompt-marketplace/troubleshooting/toss-payment-resilience-layers/)
- [상품 단위 부분환불을 위해 환불 처리 주체를 결제 서비스에서 주문 서비스로 재설계](/projects/ai-prompt-marketplace/troubleshooting/refund-request-payment-to-order/)
- [주문 검증 방식을 로컬 캐시에서 gRPC 직접조회로 재설계](/projects/ai-prompt-marketplace/troubleshooting/order-verification-cache-to-grpc/)
- [서비스 간 결합·장애 전파를 줄이기 위해 화면 데이터 조합 책임을 백엔드에서 프론트로 재설계](/projects/ai-prompt-marketplace/troubleshooting/page-composition-frontend-migration/)

각 사례에서 대안을 나열하고 트레이드오프를 비교하는 과정 자체를 AI와 함께 진행했습니다. 특히 회복성 계층처럼 여러 장치(서킷브레이커·벌크헤드·레이트리미터·재시도)를 어떤 순서로 결합할지처럼 선택지가 조합적으로 늘어나는 문제에서, 각 결합 순서가 만들어내는 부작용을 하나씩 짚어가며 논의하는 데 AI를 적극 활용했습니다.

이 논의 과정은 즉흥적인 대화로 흘려보내지 않고, Claude Code의 `superpowers` 플러그인으로 구조화했습니다. `brainstorming` 기능으로 각 결정마다 대안과 트레이드오프를 정리한 설계 문서를 먼저 작성하고, `writing-plans` 기능으로 그 설계를 실행 가능한 TDD 구현 계획 문서로 옮겼습니다. 실제 구현은 이 두 문서를 참조해서 진행했고, 그 결과가 위에 링크한 트러블슈팅 사례들입니다.

### 코드 생성과 검증

결제 승인 API, 이벤트 기반 부분환불, 감사 로그를 비롯한 대부분의 기능은 앞서 작성한 TDD 구현 계획 문서를 기반으로 Claude Code가 전체 구현했습니다. 테스트를 먼저 작성하고 그 테스트를 통과시키는 구현을 만드는 사이클 자체를 AI가 온전히 수행하는 방식입니다.

다만 AI가 전체를 구현했다는 사실이 검증을 생략해도 된다는 뜻은 아니라고 봤습니다. 그래서 이렇게 나온 코드는 항상 세 단계 검증(팀원의 코드 리뷰, 제출 전 본인의 재검토, AI에게 다시 리뷰를 요청하는 과정)을 거쳤습니다. 세 검증 주체의 관점이 서로 겹치지 않는다는 게 이 방식의 요점입니다. 팀원은 팀 컨벤션과 도메인 지식 기준으로, 저는 그 코드를 실제로 이해하고 책임질 수 있는지 기준으로, AI는 다시 한번 기계적으로 놓치기 쉬운 지점(엣지 케이스, 일관성) 기준으로 검토합니다.

마지막 단계인 "AI에게 다시 리뷰를 요청하는 과정"은 매번 다른 기준으로 봐달라고 하는 대신, 이 프로젝트의 컨벤션을 정리한 커스텀 스킬을 만들어 그 기준으로 검토하게 했습니다. 아키텍처(계층 간 의존성 방향), 도메인 모델(상태 변경 방식), 컨트롤러/예외 처리, 코드 스타일, API 문서화, Git 컨벤션, 보안, 이벤트 처리까지 여덟 개 영역을 다루는 스킬입니다.

같은 코드라도 검토 기준이 매번 달라지면 리뷰 품질이 들쭉날쭉해지는데, 이 기준을 스킬로 고정해두니 AI 리뷰가 매번 같은 잣대로 이뤄졌습니다.

### 반복 작업 자동화

개발 외적으로 반복되는 작업들도 Claude Code로 자동화했습니다.

- 커밋 전 diff를 보고 팀 컨벤션에 맞는 커밋 메시지 생성
- 대화를 통해 정해진 템플릿에 맞는 이슈 자동 생성
- 이슈 내용을 분석해 브랜치 이름 생성
- 커밋 이력을 분석해 템플릿에 맞는 PR 생성

이 작업들은 결과물의 정확성보다 일관성(컨벤션 준수)이 더 중요한 작업이라, AI에게 맡겼을 때 특히 이점이 컸습니다.

### 토큰 효율화

위에서 언급한 프로젝트 컨벤션(여덟 개 영역)을 전부 하나의 지침 문서에 몰아넣지 않았습니다. 모든 규칙을 한 문서에 담으면 어떤 작업을 하든 그 문서 전체가 매번 컨텍스트에 실려, 지금 하는 작업과 무관한 규칙까지 매번 다시 읽는 데 토큰을 씁니다. 그래서 규칙을 영역별로 분리한 별도 문서로 관리하고, 지침 문서에는 각 문서로 가는 경로만 남겨 실제로 관련 있는 작업을 할 때만 해당 영역의 문서를 찾아 참조하도록 구성했습니다.
